## 1. 为什么要 v5：实测暴露的四个确定性缺陷

### 1.1 P1：变载识别门限被 EMA 分离增益放大到 ≈27%

**症状（用户现场）**：压 10N 砝码、稳定后再加 5N（真值 15N），显示先跳到 15N 附近、随后**被拉回 10N**。

**代码事实**（`drift_compensator.cpp` 负载内分支）：

```cpp
const double div = std::abs(fast_ - slow_);
const double div_step_thr = std::max(kStepRel * std::max(slow_, eps), kStepAbsFrac * max_ts_);
const bool step_now = in_load_ ? (div > div_step_thr) : ...;
```

`fast_/slow_` 是对**总量**的一阶 EMA（τf=0.7s / τs=6.0s）。对一次阶跃 Δ，两者之差

```
div(t) = Δ·(e^(−t/τs) − e^(−t/τf))，峰值 = 0.665·Δ（t≈1.70s）
```

也就是说 **门限名义是 18%，实际等效最小可识别台阶 = 0.18 / 0.665 ≈ 27% 电平**。
低于该比例的加载不会触发 `pending` → 不 restep → 被蠕变模型当成慢相增量**积分掉**，
扣除量持续增长直到吃掉整个台阶 ⇒ 显示被拉回原电平。这正是用户描述的现象。

**量化证据（实测）**：

- `13ffca` @27.66s：真实台阶 +4672（占电平 0.24）→ **漏检**；8s 内原始走 +4900，显示只走 **+1937（41%）**，同刻被拉低到 ≈21900（原始 24160）。
- `切换负载-快相无责` @240.86s：台阶 +5254（0.256）→ 漏检 → 扣除量冲到 **9241 ADC**，显示 16600 vs 原始 25842（**欠报 36%**，持续到卸载）。
- 三份录制合并的负载内变载台账：比值 ≥0.29 的 **2/2 全部识别**，<0.29 的 **0/2 全部漏检**。

**还有第二重陷阱（v5 原型初版踩到）**：`pending` 需要连续 2.5s 保持才确认；
若用「近期窗 vs 3s 参考窗」的电平差做判据，参考窗会被台阶本身逐步污染，
差值在 2.5s 前就掉回门限以下 → **连 25% 的台阶也会漏**（20N+5N 案例）。
v5 用**锁存参考电平 + 滞回**解决（见 §2.1）。

### 1.2 P2：restep 把旧载已累积的蠕变锁进新基线

```cpp
// Restep(): A_ = a_new_acc_ / a_new_frames_  即 pending 期 Z(=v−b_) 的逐通道均值
```

`A_` 是"当前载荷对应的、已扣掉蠕变的幅度参考"。但 pending 期的 Z 里**仍然含旧载已累积的蠕变**
（10N 保压 280s 后读数已蠕变 +11.8%，加 5N 时这个 +11.8% 还在），
把它当成新基线 ⇒ 旧蠕变**从此不再被扣除** ⇒ 每次变载都留下一个 ≈已累积蠕变的永久正偏。

**实测**：台阶 50% 场景 v3/v4 稳定在 1.62×10N（理想 1.50×10N，**+7.9%**）；台阶 100% 场景 +5.9%。

### 1.3 P3：v4 的免责期不覆盖 restep（文档与代码不一致）

`Document/02` §3.3 与 `04` §3.3 都称"负载内变载同样起免责期（都经 BeginLoad）"，但：

- Python 原型 `r_fastphase.GLM53v4._restep` 不调用 `_begin`；
- C++ `DriftCompensator::Restep()` 也不调用 `BeginLoad()`（该分支注释原文即"非 BeginLoad"）。

两边都把 `fast_done_=false` 只放在「空载→负载」路径上。实测印证：v4 与 v3 的全部分歧区间
都起自 3 次 onset 之后约 3s，**16 次 restep 处没有任何冻结行为**。
（另：`Document/02` §5.3 的"v7 只在首次 onset 生效≡v3"结论也不成立——v7 的"首次 onset"
实际落在录制首帧即空载 t=0，那 503 帧免责期全程对应零负载，等于空转。）

### 1.4 P4：v4 原型在免责期内跳过状态机

`r_fastphase.GLM53v4.process()` 在函数**开头**就 `return v - self.b_`，
整段跳过 v3 的状态机 ⇒ 免责期 5s 内：EMA 全部冻结、**卸载判定失效**、
且 epoch 起点已生效的扣除被直接丢弃（卸载/变载瞬间显示会跳）。
`04-C++实现骨架.md` §3.4 给的插入点是正确的（状态机之后），是原型实现偏离了骨架。

## 2. v5 算法定义

### 2.1 ① 短滞后电平差变载检测（替代/补充 div 判据）

维护一个总量环形缓冲（1024 帧，≥5s@100Hz），每帧取两段均值：

```
lv_now = mean{ total(t') : t' ∈ (t − 0.3s, t] }          // 近期窗
lv_ref = mean{ total(t') : t' ∈ (t − 0.8s, t − 0.3s] }   // 紧邻其前的参考窗
d_lev  = lv_now − lv_ref
thr    = max( kLevRel × lv_ref , kLevAbsFrac × max_ts )   // 5% × 参考电平，下限 1% × 历史最大
```

**为什么用 0.5s 滞后差分而不是长窗电平差**：它天然区分"台阶"与"蠕变斜坡"——
实测蠕变最快也只到 ~1%/s，0.5s 内变化 0.5%，远低于 5%；
而砝码台阶是一次性跳变，**全额**呈现在这个差分里。长窗（3s）做不到这一点，
会把快相/快速蠕变误判为台阶（v5 原型初版即因此把恒载段切成 8 段 epoch）。

**判据与状态机接入**（只增敏不降敏）：

```
armed  = in_load && (t − onset_ts) > kLevArmS(3.0s)     // 避开快相与上一 epoch 的暂态
if 未锁存 且 armed 且 |d_lev| > thr:
        锁存 latch = lv_ref, latch_thr = thr            // 命中
lev_ok = 已锁存 且 |lv_now − latch| > 0.5×latch_thr     // 滞回：电平回到一半以内即解锁

step_now = (div > div_thr) 或 lev_ok                    // 两条判据取或
pending 置位   ：step_now
pending 复位   ：(not lev_ok) 且 div < 0.5×div_thr
```

**锁存（latch）是必需的**：台阶发生后，参考窗会逐步被台阶本身占据，
若每帧都重算 `|lv_now − lv_ref|`，差值会在 ~1.5s 后掉回门限以下，
而 `pending` 需要连续 2.5s → 大台阶反而漏检。

**门限取值依据（实测分离度）**：统计全受载段的 `|d_lev| / 电平`：

| 录制 | 稳定窗 p99 | 稳定窗 max | 事件沿 max | 倍数 |
|---|:--:|:--:|:--:|:--:|
| 切换负载-快相无责 | 0.85% | 2.82% | 268.2% | 95× |
| 再切换负载 | 2.71% | 3.24% | 92.4% | 29× |
| 中途切换-1d9493 | 0.23% | 0.24% | 85.3% | 363× |
| 中途切换-13ffca | 6.77% | 8.67% | 435.4% | 50× |
| 恒载 9 组 | 0.30~3.37% | 0.56~6.61% | 87~133% | 13~174× |

⇒ 真实台阶 ≥85% 电平，而"稳定段"内的最大电平波动 ≤8.7%（且多数 <3.3%，其中大的几处
经复核本就是真实加载）。**取 5%** 既留了 1.7× 的余量、又把可识别台阶从 27% 降到 5%。

### 2.2 ② restep 基线扣除已累积蠕变（修永久正偏）

```cpp
// Restep() 中，A_ 由 pending 期均值得到之后：
if (hold_comp_ 有效) {
    A_ = (A_ - hold_comp_).cwiseMax(0.0);     // ★ 扣掉旧载已累积的蠕变
    重新计算 loaded_（A_ > kLoadedFrac·max(A_)）
}
// 随后的 g_ 锚定（median(hold_comp_/(γ·A_))）保持"扣除量连续"，一行不用改
```

**为什么这一改就对了**：设旧载已累积蠕变 `c`（算法估计即 `hold_comp_`）。
修正后 `A_new = 新电平读数 − c` 就是**无蠕变参考**；而 `Z` 里那 `c` 仍在，
于是 `g_raw = (Z − A_new)/A_new ≈ c/A_new > 0`，扣除量自然**继续**维持在 `c`，
显示既不跳变、也不再留下 `c` 的永久偏移。

### 2.3 ③ 免责期：onset 与 restep 都生效，且保留 epoch 起点扣除

```
_begin(ts)  ：… ; fast_done=false; carry=0;          exempt_acc=0; exempt_n=0; lev_latch=清
_restep(ts) ：… ; fast_done=false; carry=当前扣除;    exempt_acc=0; exempt_n=0; lev_latch=清
```

**`carry`（epoch 起点已生效的逐通道扣除）是连续性的关键**：
免责期内输出 `Z − carry`，而不是 v4 的 `Z`（只扣零漂基线）。
- 空载→负载：`carry = 0`，输出 = `Z`（与 v4 相同）；
- 负载内变载：`carry = 变载前那套扣除`，变载瞬间显示**不跳变**，
  并且（配合 ②）旧蠕变继续被扣。

**免责期内不做的事**：不积分 `g`、不使用 v3 的 A 窗、不累积蠕变——
但**不重置** `g2_acc_ / g_rel_acc_ / gamma_`。
（v3 的 `Restep()` 同样刻意保留它们：γ 是器件属性、不是 epoch 属性；
一旦重置，紧随其后的任何一次台阶都会把 γ 一帧拉飞——v5 原型初版正是这样把
两档间隔 8s 的场景做坏成 −10.9%。）

### 2.4 ④ 免责期分支插在状态机之后

与 `04-C++实现骨架.md` §3.4 的插入点一致：`in_load_` 迁移、阶跃/卸载判定、
基线 `b_` 跟踪、`pending` 期 `a_new_acc_` 累积**都在免责期内照常运行**。
免责期只决定"这一帧的输出怎么算"和"epoch 何时重新捕获 A"。

### 2.5.1 运行期切换免责期（菜单两档）

免责期长度**不再是编译期常量**，改为成员 `fast_phase_s_` + 公有接口：

```cpp
void DriftCompensator::SetFastPhase(double fast_s);        // fast_s > 0 才生效
double DriftCompensator::fast_phase_s() const;
static constexpr double kFastPhaseDefaultS = 3.0;          // 菜单「无责 3s」
static constexpr double kFastPhaseAltS     = 5.0;          // 菜单「无责 5s」
```

- `SetFastPhase(fast)` 同步推导：`exempt_awin_s_ = fast / 3`、`lev_arm_s_ = fast`；
- `DriftCompensationCoordinator::SetFastPhase(fast)` 记录全局值：
  **值变化时 `ResetAll()`**（与开关切换同语义，避免新旧参数混在同一段估计里），
  且在每次 `Process()` 里对新/老条目 `SetFastPhase(fast_phase_s_)`，保证多设备场景下所有目标一致；
- 5s 档的幅度窗为 `[3.33, 5.0]s`（此前 A/B 表用的是 `[3.5,5.0]s`）——
  实测两者差异 **<1%**（最大偏差 2031→2067 ADC、捕获比完全相同，见 `scripts/bi_v5_5s_awin.py`），
  故 §0 与 §4.7 的 5s 列数据可直接沿用。

**菜单接线**（`src/ui/menubar.{h,cpp}` → `src/app/application_controller.cpp` → `src/data/data_handler.{h,cpp}`）：

```
设备
 ├ 设备连接
 ├ 工厂模式
 ├ 时漂/零漂补偿（无责 3s）      ← 新
 ├ 时漂/零漂补偿（无责 5s）      ← 新
 └ ...
```

- 两项**互斥**（勾一个自动取消另一个）；**再点已勾选的一项 = 关闭补偿**；
- 信号 `FileMenu::DriftCompensationToggled(bool enabled, double fast_phase_s)`；
- 控制器经 `Qt::QueuedConnection` 投递到数据线程：

### 4.5 自检断言（四项，必须实现）

`Document/02` §6 列的三条断言在 v5 上同样适用，且**新增一条针对本版修复的断言**：

1. 免责期结束后 `A_` 非零；
2. `loaded_` 中为真的通道数 > 0；
3. `g_` 随慢相单调增长（非恒 0）；
4. **（新增）每次 restep / 免责期收尾后，逐通道扣除量 `γ·A·g` 与 `carry_` 之差
   ≤ 该通道幅度的 5%** —— 即"扣除量连续、旧蠕变没被丢掉"。
   若 `carry_` 恒为 0，说明基线修复未生效（会退回 P2 的正偏）。

实测自检（四份录制，v5@3s）：`A_max = 2866 / 2929 / 3153 / 3432`（非零）、`loaded = 12~14`、
`γ ∈ [0.30, 2.00]`（在用）。

### 4.6 残留问题与"看起来更差"的解释

- **13ffca 的 epoch 数 v5=8 / v3=4**：该录制确有 5~6 次真实载荷变化，
  v5 多出的几次是**正确识别**（每次识别都会重启蠕变 epoch）。代价是：
  载荷每 10s 变一次的工况下，蠕变模型（τg=3s）**来不及收敛** ⇒ 该段显示基本跟随原始。
  这是"跟得上载荷"与"压得住蠕变"之间的固有取舍；v5 选择前者（因为吃真实载荷更不可接受）。
- **恒定长保压**（>60s 无变载）工况下 v5 与 v3/v4 同档（4.3 表 0.04~0.32%，免责 3s 版）。

### 4.7 免责期 3s vs 5s 的取舍（本次由 5s 改为 3s 的实测依据）

**结论**：长保压指标 3s 更好，变载跟踪指标 5s 更好；本次按需求取 **3s**。

| 指标 | 免责 5s | 免责 3s（当前） | 谁更好 |
|---|:--:|:--:|:--:|
| 恒载 9 组 全段 / 慢相段 | 2.41% / 1.50% | **1.88%** / 1.61% | 3s（全段） / 5s（慢相） |
| 恒载 9 组 受载中位 / 噪声比 | 1.49% / 0.78 | **0.92%** / **0.73** | 3s |
| 实录 台阶捕获比 中位 / 最小 | **0.99 / 0.87** | 0.98 / 0.85 | 5s |
| 实录 变载窗最大偏差 中位 | **956** | 1681 | 5s |
| 实录 全程最大偏差（切换负载 / 13ffca） | **6.9% / 4.3%** | 9.0% / 8.8% | 5s |

**为什么免责期越短、变载后的偏差反而越大**（这是本次改参数后最值得注意的一点）：

- 免责期的长度**同时决定 `A` 的采集时刻**：A 取自 epoch 起点后 `[kFastPhaseS−kExemptAWinS, kFastPhaseS]`；
- 而 epoch 起点 = **真实台阶 + 2.5s**（阶跃确认滞后 `kStepPersistS`）。
  于是 3s 版的 A 落在**真实台阶后 4.5~5.5s**，5s 版落在 **6.5~7.5s**；
- 现场用砝码加载时，读数在台阶后 **5~7s 才基本稳定**（机械加载 + 接触建立 + 手放砝码的过程），
  所以 3s 版的 A 常偏小 → 相对残差 `(Z−A)/A` 偏大 → `g` 偏大 → 扣除量偏大 → **变载后显示偏差更大**；
- 长保压段则相反：3s 版"放过去的快相增量"更少，所以全段/受载中位/噪声比都更好
  （与 v4 文档 §5.2 的结论一致）。

⇒ **选型建议**：以"长保压时漂"为主要验收口径 → 用 3s；以"切换负载跟得上"为主要口径 → 用 5s。
若想两头兼顾，可考虑 **4s**（本文件未做该点位的实测，需要时按 §8 复现流程对 4.0/4.5 做一次扫描）。
改回 5s 只需三处常量：`kFastPhaseS=5.0`、`kExemptAWinS=1.5`、`kLevArmS=5.0`
（Python 原型：`FAST_S`、`EXEMPT_AWIN`、`LEV_ARM_S`）。

## 5. 代价与已知限制

1. **低于 5% 电平的变载仍会被当成蠕变**。这是本版留下的下限（原来是 27%）。
   若现场有 <5% 的小幅加载需要被看见，继续下调 `kLevRel` 需同步接受
   快速蠕变/操作抖动引发的 epoch 重启（见 §4.6）。
2. **免责期内读数仍会高出真值约快相增量**（16~33%），与 v4 相同；
   但 v5 在变载处**保留旧扣除**，因此变载瞬间不会有 v4 那种"扣除归零"的跳变。
3. **`kStepSuppressS = 6s` 未改**：epoch 起点后 6s 内的第二次变化只能冻结不能 restep；
   §4.1 场景 6/7 显示两档合并处理的结果仍在 ±0.3% 内，故暂不改。
4. **多通道 γ 在频繁变载下不易收敛**（v3 遗留性质）：epoch 重启会保留 γ 的积分，
   但在"每 10s 一次变载"的录制里 `γ` 仍可能长时间停在 1.00（第 4.2 节 13ffca）。
5. **参数由 4 份实采录制（ADC 域）+ 恒载 9 组标定**，尚未在**力值域**、跨载荷量级
   （5N/10N/20N 标定后）与**短保压（<5s）**工况上验证。
6. **已落地**（`src/domain/drift/`），但**只做了编译验证 + 离线对拍，未做真机手测**——
   界面/真机验证仍按项目规范交由用户执行。

```cpp
void DriftCompensator::SetFastPhase(double fast_s) {
    if (!(fast_s > 0.0)) return;
    fast_phase_s_  = fast_s;
    exempt_awin_s_ = fast_s / kFastPhaseWinRatio;   // 3s → [2.0,3.0]s；5s → [3.33,5.0]s
    lev_arm_s_     = fast_s;                        // 武装延时跟随免责期
}

void DriftCompensator::PushLevel(double ts, double total) {
    const int i = static_cast<int>(lev_n_ % kLevHistN);
    lev_ts_[i] = ts; lev_v_[i] = total; ++lev_n_;
}
bool DriftCompensator::WinMean(double t0, double t1, double* out) const {
    const long n = std::min<long>(lev_n_, kLevHistN);
    double s = 0.0; int c = 0;
    for (long i = 0; i < n; ++i)
        if (lev_ts_[i] > t0 && lev_ts_[i] <= t1) { s += lev_v_[i]; ++c; }
    if (c == 0) return false;
    *out = s / static_cast<double>(c);
    return true;
}
void DriftCompensator::CurrentDeduction(Eigen::VectorXd* out) const {
    out->setZero(n_);
    for (int i = 0; i < n_; ++i)
        if (loaded_[i] && A_(i) > 1e-9)
            (*out)(i) = std::clamp(gamma_(i) * A_(i) * g_, kCreepLoFrac * A_(i), kCreepHiFrac * A_(i));
}
```

**(b) 阶跃检测**（`const bool step_now = ...` 处）替换为：

```cpp
    // ── v5(P1): 短滞后电平差判据（与 div 判据取或，只增敏不降敏）──
    bool lev_ok = false;
    if (in_load_ && lev_n_ > 3) {
        double lv_now = 0.0, lv_ref = 0.0;
        if (WinMean(ts - kLevFastS, ts, &lv_now)) {
            if (lev_latched_) {
                lev_ok = std::abs(lv_now - lev_latch_) > kPendingResetFrac * lev_thr_;
                if (!lev_ok) lev_latched_ = false;      // 电平回到一半以内 → 解锁
            } else if (ts - onset_ts_ > kLevArmS) {
                if (WinMean(ts - kLevFastS - kLevLagS, ts - kLevFastS, &lv_ref)) {
                    lev_thr_ = std::max(kLevRel * std::max(lv_ref, eps), kLevAbsFrac * max_ts_);
                    if (std::abs(lv_now - lv_ref) > lev_thr_) {
                        lev_latch_ = lv_ref; lev_latched_ = true; lev_ok = true;
                    }
                }
            }
        }
    }
    bool step_now = in_load_ ? (div > thr) : (div > thr && fast_ > slow_);
    if (in_load_ && lev_ok) step_now = true;
    if (step_now) {
        if (!pending_) { pending_ = true; pending_ts_ = ts; }
    } else if (pending_ && !lev_ok && div < kPendingResetFrac * thr) {
        pending_ = false;
    }
```

**(c) 两个卸载分支**（`else if (u > kUnloadFastS && idle)` 与 `else if (... && idle)` 内的
"负载→空载"）各追加两行：

```cpp
        fast_done_ = true;
        lev_latched_ = false;
```

**(d) 免责期分支**（插在状态机/基线块之后、`Eigen::VectorXd Z = v - b_;` **之前**）：

```cpp
    // ══ v5(P3/P4): 快相免责期 —— 状态机已跑完，这里只决定输出与 epoch 收尾 ══
    if (in_load_ && !fast_done_) {
        const double ux = ts - onset_ts_;
        if (ux < kFastPhaseS) {
            a_captured_ = false;
            a_acc_.setZero(n_);
            a_frames_ = 0;
            g_ = 0.0;                         // 不重置 g2_acc_/g_rel_acc_/gamma_
            if (hold_ && hold_comp_.size() != static_cast<Eigen::Index>(n_))
                hold_comp_ = carry_;          // 与 carry 一致，保持连续
            Eigen::VectorXd Zx = v - b_;
            if (ux >= kFastPhaseS - kExemptAWinS) {
                exempt_acc_ += (Zx - carry_);
                ++exempt_frames_;
            }
            v = Zx - carry_;                  // 直通 + 保留 epoch 起点扣除
            return;
        }
        fast_done_ = true;                    // ── 免责期结束当帧 ──
        if (exempt_frames_ > 0)
            A_ = exempt_acc_ / static_cast<double>(exempt_frames_);
        else
            A_ = v - b_ - carry_;
        A_ = A_.cwiseMax(0.0);
        const double amax_e = A_.maxCoeff();
        if (amax_e > 1e-9) {
            for (int i = 0; i < n_; ++i) loaded_[i] = A_(i) > kLoadedFrac * amax_e ? 1 : 0;
        } else {
            std::fill(loaded_.begin(), loaded_.end(), 0);
        }
        a_captured_ = true;
        g_ = 0.0;
        scratch_.clear();
        for (int i = 0; i < n_; ++i)
            if (loaded_[i] && A_(i) > 1e-9) scratch_.push_back(carry_(i) / A_(i));
        if (!scratch_.empty()) {              // 扣除连续性锚定
            const auto mid = scratch_.begin() + static_cast<long>(scratch_.size() / 2);
            std::nth_element(scratch_.begin(), mid, scratch_.end());
            g_ = std::clamp(*mid, 0.0, 1.0);
        }
        carry_.setZero();
        exempt_acc_.setZero();
        exempt_frames_ = 0;
        // 不 return：当帧继续走 v3 的蠕变补偿逻辑
    }
```

> 编译注意（沿用 `04` §3.0 的教训）：
> ① `carry_`/`exempt_acc_` 的尺寸只能在 `ResetFor(n)` 里设置，不能类内初始化；
> ② `A_ = (hold_comp_.size()==n_) ? ... : ...` 这类 Eigen 三元表达式两分支类型不同会编译不过，
>    必须像上面那样先赋兜底值再覆盖；③ `hold_comp_` 与 `carry_` 比较尺寸时用 `static_cast<Eigen::Index>(n_)`。

## 10. v5.1 修订：取消空载强制归零（算法保持连续行为）

> 用户报告（2026-09-17）："v5 对零点的抑制非常厉害，会导致零点快速塌陷进 0"；
> 用户裁决：**"空载不需要归零……算法是需要一直行为的，但是这个不需要强制拉回调零。"**
> ⇒ 只去掉"把空载读数拉回 0"这条链路（基线归零），**算法本身照常连续运行**（不停扣、不停跑、不重置）。

### 10.1 现象与三条成因

排查见 `../scripts/bj_probe_zero.py`、`bl_decompose_zero.py`、`bn_trace_baseline.py`：

1. **显示层阈值钳位是"塌陷进 0"的最后一刀**：`ProcessingPipeline::ApplyThreshold`
   （对照 Python `data_1d[data_1d < effective_threshold] = 0`）把低于阈值（默认 0）的显示值一律置 0。
   补偿后若算出负值，界面上看到的就是**硬 0**，不是"被抑制到 0"。
2. **v3 的"卸载门控自动归零"把零点强制拉回 0**：空载期以 τ=2s 跟踪基线 `b_` 并减掉。
   更糟的是门控（`ts_smooth_ < 0.2×max_ts_`）用的是 0.3s 平滑电平，**加载沿那 0.2~0.3s 仍放行**：
   实测（21ch 录制）加载沿 38.95→39.24s 期间 `b_` 总量 52.5 → 944.1 后被冻结，
   这 944 ADC（≈45 ADC/通道）成了卸载后零点上的**负偏置**，只能按 τ=2s 衰减（约 6~8s 才回 0 附近）。
3. **读数已接近 0 时仍在扣蠕变**（既有行为，保留）：pending 期冻结的 `hold_comp_` 与免责期 `carry_`
   冻的是**跌落前**的 γAg；v5 的 5% 电平判据在跌落沿 1~2 帧就命中（v3 的 div 判据要等约 0.2s，
   那时 g 已从 0.05 崩到 ≈−0.01）⇒ 实测卸载沿后首个 0.5s 显示总量 v5 为 −1649/−1852/−2503 …
   （原始仅约 25 ADC）。**本条不通过"停扣"解决**（那会把算法停掉），而是靠 §10.2 ② 的输出封顶，
   让算法继续按原样行为、只是不把界面压到负值。

### 10.2 代码改动（`src/domain/drift/drift_compensator.{h,cpp}`）
