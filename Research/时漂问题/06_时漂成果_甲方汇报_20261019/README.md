用 `parity_dll.py` 在**两份实录全帧**上跑 C ABI（`dv6_portable.dll`，产品同源代码）：

| 检查 | 拇指 | 掌心 |
|---|---|---|
| `dv6_params` 结构体字节数 | DLL 264 == ctypes 264 ✅ | 同 |
| 修复档 gate=1：C vs Python `core.py` 逐帧最大差 | **0.000** | **0.000** |
| 修复档 gate=1：恒载首尾漂移 | +19.2 ADC | −635.4 ADC |
| 现场档复刻 vs 录制实测 `algoadc`（逐帧平均差） | 0.37 ADC | **12.85 ADC** |

两条要紧的：

1. **修复档（`floor_rise_idle_only=1`）的 C 实现与 Python 参考实现逐帧完全一致**（0.000），
   本次两份数据都复核过。修复结论不是某一份实现的偶然。
2. **现场档 `guard=1` 的 Python 复刻不可用于逐帧结论**：掌心 96 min 上平均差 12.85 ADC、
   首尾漂移差 2650 ADC（拇指仅 0.37 ADC）。误差按四分位分布为
   `[44.8, 6.6, 0.02, 0.03]`——前 25% 发生一次通道级边界分叉后沿不同稳态走到底。
   这印证了 05 报告 §6.6 的注记，**K10（`guard=1`）档要以 C 实现或实测为准**。
   因此本包"升级前"一律用录制实测 `algoadc`，不依赖该复刻。

## 3.1 为什么把 `r_slow_max` 从 0.6 收到 0.25

现场值 0.6 的问题不是漂移，是**读数会先往下掉**（慢态把真实载荷当成蠕变扣掉了）。
扫描（`sweep_rslow.py`，修复档，窗口不变，单位 ADC）：

| r_slow_max | 拇指 drift | 拇指 p2p | 拇指下探 | 掌心 drift | 掌心 p2p | 掌心下探 |
|---:|---:|---:|---:|---:|---:|---:|
| 0.10 | +332 | 556 | 113 | +511 | 762 | 125 |
| 0.15 | +187 | 466 | 153 | +351 | 620 | 141 |
| 0.20 | +190 | 487 | 161 | +141 | 438 | 168 |
| **0.25** | **+198** | **515** | **172** | **−59** | **436** | **287** |
| 0.30 | +215 | 543 | 177 | −209 | 562 | 413 |
| 0.40 | +183 | 545 | 200 | −400 | 706 | 556 |
| 0.60 | +19 | 516 | **313** | **−635** | **930** | **780** |

- **下探**（读数相对起点向下的最大幅度）随 `r_slow_max` 单调下降：掌心 780 → 287（−63%），
  拇指 313 → 172（−45%）。
- **0.25 是掌心唯一同时满足「首尾变化 ≈ 0（−59 ADC）且起伏最小（436 ADC）」的点**；
  0.6 时掌心既不达标（−635）又起伏最大（930）。
- 拇指在 0.6 时首尾变化更好（+19），但那正是"把载荷吸进慢态"换来的，且下探 313 ADC。

合成恒载检验（`synth_hold.py`：载荷严格恒定 30000 ADC、零点漂移 +600 ADC/60 min、
噪声 σ=3/通道、种子 20261019）给出这件事的上界：

| r_slow_max | 60 min 后输出相对真值 | 换算 |
|---:|---:|---:|
| 0.10 | −2878 ADC | −2.9 N |
| 0.25 | −5986 ADC | −6.0 N |
| 0.60 | **−11006 ADC** | **−11.0 N** |

严格恒载下慢态会一路涨到上限 `r_slow_max·e`，稳态扣掉载荷的比例约
`r_slow_max / (1 + r_fast + r_slow_max)`：0.6 → 约 38%，0.25 → 约 19%。
真实数据漂移更快、慢态未跑到上限，所以没这么夸张，但方向与量级一致。
**这是慢态上限的结构性副作用，不是换一个参数就能根治的**——要根治得让 `x_slow`
随载荷缩放，或给慢态加"是否真的在蠕变"的判据（05 报告 §8.7 已列为遗留项）。

## 6. 已知风险（对外口径前请先定）

1. **`r_slow_max=0.25` 压住了下探，但削弱了慢态抗漂能力**：拇指首尾变化从 0.02 N 退到 0.20 N
   （仍在 0.30 N 线内）。更长按压时长（>2 h）下补偿是否够用未验证，需要长录制复验。
2. **慢态上限的结构性副作用还在**（见 §3.1）：严格恒载下慢态会扣掉约
   `r_slow_max/(1+r_fast+r_slow_max)` 的真实载荷。0.25 把这个比例从 38% 降到 19%，
   没有消除。要根治得改 `x_slow` 的缩放方式或加"是否真的在蠕变"的判据。
3. 掌心、四指指腹"升级前"的现场档补偿在评价段内几乎归零（末段只剩首段的 1.5% / 0.2%），
   所以它们更像"直通 + 信号自身漂移"；与拇指那条"补偿逐级塌陷"的机理不完全同型，
   对外叙述时不要混为一谈。
4. **四指指腹升级后 0.26 N 贴验收线**，余量只有 0.04 N。这一组不太适合当"达标"样板，
   要收紧的话得再调 `r_slow_max`（见 §3.1 的权衡）。
4. 表格 / 卡片里的数字全部由 `out/metrics.json` 生成，改口径必须重跑脚本，不要手改 PPT。
5. `run_analysis.py` 的 `metrics.json` 是读-改-写，**不要并行跑不同 key**（会互相覆盖）；
   需要两份一起跑时用 `run_analysis.py thumb palm` 串行。
